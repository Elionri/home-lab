Personal home laboratory for learning Security Operations Center (SOC), threat detection and incident analysis.

# About

**Цель проекта:** Демонстрация навыков построения инфраструктуры информационной безопасности и базового анализа событий с использованием ИИ на позицию SOC Analyst L1.

# Описание

Данный проект представляет собой локальную лабораторную среду (Home Lab) на базе виртуальной машины с ОС Ubuntu и отдельного компьютера с установленой ОС Ubuntu. Весь стек развернут для изучения работы SIEM-системы Wazuh, а так же изучения взаимодействия его с ИИ. В рамках проекта настроен агентский сбор логов, централизованное управление политиками безопасности, анализ алертов с помощью локальной ИИ, а также базовые сценарии корреляции для обнаружения грубых атак (брутфорс, сканирование портов, изменения критичных файлов).

*Проект является демонстрационным и развернут в изолированной среде.*

Возился с этим часа два, а ,как оказалось, все гораздо проще:

#### Решение ошибки `external volume wazuhlogs not found `
Перво наперво нужно ввести `docker volume ls`, чтобы посмотреть как наш wazuh_logs называется на самом деле. Для удобства можете добавить к этой команде `| grep wazuh`, в таком случае нужно будет найти volume с припиской `_logs`. В моем случае - `single-node_wazuh_logs`. И вот в чем дело. В файле `docker-compose.wazuh.yml` в самом низу есть блок:
```bash
volumes:
  wazuhlogs:
    external: true
    name: ${переменная}-wazuh_logs
```
Точно сейчас не вспомню, но если найду отредактирую так, как было. По какой причине он не смог найти мой volume, я так и не понял, и время было позднее. Решил радикально. Прописал так: `name: single-node_wazuh_logs`. Причина, по которой я возился несколько часов, была простой невнимательности. В файле `.env` два блока `volumes:` Один в внутри блока `wazuh_ingest`, а второй отдельно блоком `volumes:`, в файле он находится в самом низу. Так вот менял я первый. Если кратко - в нем должно находится стандартное название `wazuh_logs`, а вот во втором блоке (в нижнем), уже то, которое у нас существует в системе, то есть `single-node_wazuh_logs`.

![Два блока volumes](images/Pasted%20image%2020260920015928.png)

#### Решение проблемы с нехваткой памяти на диске
Да, это была вторая проблема, которую я не смог проигнорировать. Места было дай бог сто мегабайт. Пошагово ниже разложу как именно я решил эту проблему:
1. Выключаем систему, заходим в настройки
2. Выбираем `Expand..`, выбираем необходимое количество памяти, и ждем завершения процесса.
3. Включаем виртуалку, прописываем `df -h` - убеждаемся в том, что места больше не стало. Прописываем `lsblk` - /dev/sda должен увеличиться. У меня он стал больше, так что идем далее.
4. Прописываем `sudo growpart /dev/sda/2` - где 2 это номер нашего раздела, который нужно увеличить.
5. Прописываем `sudo parted /dev/sda print`- запоминаем номер раздела, у меня он 2
6. Прописываем `sudo parted /dev/sda`, далее `resizepart 2 100%`, где 2 это номер нашего раздела, который мы узнали выше. `quit` - выходим.
7. Прописываем `sudo partprobe /dev/sda ` - сообщаем ядру об изменениях, и `sudo resize2fs /dev/sda2` - расширяем файловую систему.
8. Готово.

 ```bash
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
 ```

### Проверка работы TriageWall
Для этого на хосте с агентом пишем команду `ssh bad:localhost` и трижды вводим любой пароль. Если у вас вместо поля ввода пароля вылезло `connection refuced`, то не печалимся. Рекомендую сразу прописать `sudo apt install ssh`, затем в настройках системы включить это самое подключение через ssh (secure shell), и далее `sudo ufw allow 22/tcp`. И повторяем попытку подключения `shh bad@localhost` Через какое то время, если вы наблюдаете нагрузку на **GPU**, вы увидите, что модель загрузилась в память, и обработала наш запрос. Увидеть ответ можно в веб интерфейсе TriageWall.
